# 運用書式と確認場面

## 開始するとき

本人への説明は、誰のどの課題を分担して解決するか、親と担当の役割、成果物、完了条件を短く示す。新しいチャットや連絡の許可が不足している場合は、不足する対象・方向・範囲だけを確認する。既存の許可済み担当へ同じ確認を繰り返さない。

複数チャットでの協調を頼むときの例：

> この作業を親チャットで全体管理し、APIと画面をそれぞれ別チャットで進めてください。親と各担当の間で、この作業の依頼・報告・修正連絡を相互に送って構いません。共有ファイルの担当を一人に決め、完成したものと未確認事項を親で照合してください。

これはチャット作成と当該作業の相互連絡を依頼する例である。公開・外部投稿・課金・merge等は、それぞれの本人承認範囲を別に照合する。

### 担当一覧の最小項目

| task | チャットID / host | 役割・範囲版 | owned paths | 依存 | 状態・次の担当 | 最新報告・証拠 |
|---|---|---|---|---|---|---|
| W-01 | 実際のIDとhost | API / 1.0 | 対象path | 契約C-01 | 作業中・API担当 | 計画anchor、head、報告参照 |

親、共有計画writer、連絡許可の参照先、cursorは一覧の共通欄に置ける。既存のtask記録に同じ情報がある場合はリンクし、二重管理しない。

## 担当へ渡す依頼

通常のWork Packetへ、次の協調情報を添える。参照だけで必要事項を省略せず、担当が読める絶対pathを使う。

```text
task: W-01 / 担当範囲版1.0
目的・完了条件: 誰が何をできるようになるか、何で確認するか
正本: 計画HTMLの絶対path#anchor / 計画版
担当: チャットID、host、役割
親・報告先: チャットID、host
連絡許可: 本人指示の参照と、許可された対象・方向・話題
owned paths / 範囲外: ファイルまたは責務、共有ファイルの唯一writer
基点: repository/worktree、base head、必要ならseedのhash
依存・型契約: 先行成果物、担当、現物の参照
受入ID・検証: 対象ケース、必要な証拠、未完了gate
外部操作: 許可範囲と本人指示の参照。不要なら不要と記す
引渡し: 自分の差分、対象head、検証、残件、次に動く担当
他担当の変更を戻さず、競合する場合は編集前に親へ報告する。
```

## 報告するとき

```text
task W-01 / 引渡し / 報告ID W-01-R03
対象: 担当範囲1.0、計画2.1、head <実際のSHA>
確認済み: 変更内容と、受入IDごとの実行結果
未確認・問題: 未実施、skip、失敗、回答待ちを分けて記す
証拠: 成果物・差分・ログの絶対pathまたは固定URL
次の対応: 親に受入照合を依頼。依存先W-02はその後に着手可能
```

### 報告種別と親の対応

| 種別 | 担当が伝えること | 親の対応 |
|---|---|---|
| 開始 | 正本・基点・範囲の確認 | 一覧を更新。矛盾があるときに調整 |
| 依存完了・重要変更 | 新しい成果物と影響先 | 実物を照合し、必要な担当へ共有 |
| 問題・相談 | 事実、影響、試したこと、必要な判断 | 範囲・依存・本人判断を整理 |
| 引渡し | 自分の差分、検証、残件 | 受入を照合し、統合結果を返す |
| 修正後 | finding ID、修正head、再確認証拠 | 指摘と影響範囲を再確認 |
| 停止・完了 | 実行中処理、途中結果、残件 | 所有権と全体の未完了条件を確認 |

問題の連絡は対応が必要な担当へ絞る。全員への一斉送信や、同じ内容の再送を既定にしない。報告IDと対象版で既受信を確認する。

## 中断・引継ぎ・再開

1. 親は停止対象と理由を明示し、許可された方向で伝える。
2. 担当は新規処理を止め、実行中処理と外部副作用の結果を確認する。中断できない処理は未確定と明記する。
3. 現行計画、対象head、worktree、担当差分、実行結果、未完了gate、次の一手を保存する。secretを含めない。
4. 親は旧writerの停止・担当解除を確認する。不明なら同じファイルへ新writerを入れない。
5. 再開担当は現物と現在の本人指示を照合し、取得済み証拠の適用範囲と残件を確認して開始を報告する。

連絡ツールの失敗時は、失敗を記録し、メッセージIDや相手の状態から到達を確認する。二重実行の可能性を確かめずに同じ開始依頼を再送しない。送信不能なら文案と未送信状態を残し、担当が動いたことにしない。

## 導入・改訂時の机上確認

次の場面を手順へ当てはめ、期待動作になるか確認する。机上照合は実チャットでの到達・実行の検証と区別する。

| 場面 | 期待する動作 |
|---|---|
| 「APIを直して」という単独依頼 | このスキルだけを理由に新しいチャットを作らない |
| 新規二担当と親の相互連絡を本人が明示 | 許可範囲を記録し、専用ツールで作成・準備完了を確認して分担 |
| 親からの依頼だけに「結果を返信して」とある | 返信方向の本人許可を確認。不足なら勝手に送らない |
| 両担当が同じ型ファイルを必要とする | 唯一writerまたは順序を決め、契約を共有してから編集 |
| 別worktreeの成果物に他担当の差分が混在 | base/seed/親ファイルを照合し、担当自身の差分だけ統合 |
| 依存担当がidleで更新時刻が古い | 失敗と断定せずcompact snapshotと必要な証拠を確認 |
| 担当から「完了」、CIにskipがある | 受入と証拠を読み、成功・skip・未確認を分けて記録 |
| 計画またはheadが更新された | 影響差分と証拠を再確認し、旧結果を履歴へ移す |
| 本人の訂正で既存findingの前提が変わる | 本人指示を照合し、該当指摘を訂正・撤回して関係担当へ共有 |
| 同じ報告が再び届く | 報告IDと対象版で重複を確認し、再修正や再審査を起動しない |
| 停止中の担当を交代する | 旧writer停止・差分・実行中処理を確認して所有権を移す |
| 監視対象の全受入が完了する | 全体結果を報告し、該当する既存監視を停止 |
